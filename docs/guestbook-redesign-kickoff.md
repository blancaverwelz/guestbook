## 1. What & who — existing product and desired change

- **Project and users:** Multi-event wedding/birthday/celebration web application, currently called "Wedding & Birthday Guestbook" in the repository. Event guests open a published event at `/events/[slug]`, read event details, leave a message at `/message`, browse approved messages at `/guestbook`, and contribute/view photos at `/gallery`. Event hosts/admins manage events and moderate messages/photos through protected admin routes. Different events have independent slugs, content, and accent colors.
- **Requested change (confirmed):** Transform the guest-facing Guestbook from a flat, repetitive vertical message list into a premium, modern, emotionally engaging **Memory Archive**: editorial introduction, distinctive but controlled message-card treatments, visually layered layout, thoughtful interactions, and usable exploration when hundreds or thousands of approved messages exist. Preserve clear, accessible reading and message submission. A full-site redesign is **not** requested.
- **Problem (confirmed by screenshot and code):** `GuestbookFeed.tsx` renders one same-sized `MessageCard.tsx` per message in a single column. The page has a generic title, no clear hierarchy/occasion, no search or sorting controls, no displayed approved-message total, and automatic intersection-observer loading that risks becoming a lengthy, monotonous feed. Long notes expand the vertical list dramatically. Current cursor pagination orders by `created_at` alone.
- **Expected outcome / useful release:** A complete event-specific Guestbook that feels like a keepsake at 1, 10, 100, and 1,000 messages; lets a guest locate a name or phrase across the **entire approved archive**, choose newest/oldest order, read long entries comfortably, see a trustworthy message count, and navigate messages deliberately without losing position. Guests can still submit a message through the existing workflow. Real-world accessibility, performance, and moderation/privacy remain intact.
- **Constraints:** Continue using the existing Next.js/Supabase/Vercel project unless a specific evidence-based limitation warrants change. Mobile-first; works on phones, tablets, desktop, touch, keyboard, and reduced-motion settings. Respect event-specific accents and system light/dark preference. No dedicated design assets, delivery date, traffic forecasts, budget, production database access, or event-time-zone setting were supplied. Plan for 1,000+ approved messages without downloading them all. Do not assume every event is a wedding or hard-code romantic copy.
- **Preserve:** `/events/[slug]`, `/message`, `/guestbook`, `/gallery`; the published-event gate; server-generated metadata and canonical URLs; per-event theme provider and guest navigation; admin moderation semantics; existing guest message data, form constraints (name 1–80 and message 1–500 characters), server-side submission/rate limit, event separation and RLS, gallery workflow, PWA behavior, and shared footer. Preserve existing Git/local changes in the execution checkout. Never use a service-role key in browser code.
- **Product direction approved for planning:** **Memory Archive** with luxury editorial/scrapbook-inspired styling, high visual craft, depth, restrained animation, diverse but coherent cards, and deliberate discovery. Exact token values, optional featured-message administration, and schema modifications are proposed implementation decisions, **not yet separately approved**.

- **Data changes:** Existing `messages(id, event_id, name, message, status, created_at)` and `events` tables suffice for core redesign. Query an **exact count** of approved messages; use `(created_at DESC, id DESC)` and corresponding ascending keysets for stable pagination. Add a composite database index only if query plan/test shows it necessary; existing index is `(event_id, status, created_at DESC)` and does not include `id`. Query-based name/body search is required; measure first at realistic scale before adding `pg_trgm`/GIN or a dedicated search endpoint. Schema/data transformation is **not assumed**. A security migration may be necessary for Broadcast, but requires a reviewed plan and safe staging verification. Host-selected featured messages would require separate persistence/admin control and are **deferred**.
- **Read/write/moderation contract (CRUD review):** **Create:** guest inserts via validated/rate-limited `/api/messages` only; row starts pending. **Read:** public guestbook shows approved rows for a single published event, including counts/search/subscriptions; no anonymous access to pending or rejected content. **Update:** admin approve/reject changes public membership and total/search results, not only card visibility. **Delete:** removed approved row disappears on refetch and ideally in realtime; no dangling featured preview. Ensure consistent behavior across two browser sessions and when moderation changes while a page is paginated or searched.

### Mandatory clean-code rules

1. **No layered overrides or duplicate implementations.** Modify the original source of behavior/styling; do not append contradictory Tailwind classes/CSS overrides, duplicate selectors/components, parallel feed hooks, or patches that hide a broken original.
2. **Clean edits are allowed and expected.** No blind overwriting of user changes or speculative re-scaffolding. A cohesive replacement of a verified affected component is preferable to stacking variants. Protect unrelated behavior.
3. Give each file one coherent responsibility. Separate view, query construction, state orchestration, and infrastructure where useful; avoid giant components, circular imports, hidden side effects, and premature abstractions.
4. Consolidate shared rules, delete superseded imports/styles/paths after reference checks, follow sound Next.js/React conventions, and never duplicate permission logic as a substitute for RLS.
5. Do not adopt complexity merely because the UI should look sophisticated. Prefer CSS Grid + modest variants over a heavy masonry/virtualization library unless measurement justifies it.
6. Any temporary adapter must identify its reason, removal condition, and roadmap item. Deliver complete, coherent edits; never require manual stacking of code snippets.

| Stable batch paging | Integration/fixture test with >=45 messages including duplicate timestamps; traverse newest and oldest | Every approved row returned exactly once, in stable order, with correct final-page/hasMore behavior. |
| Correct submit semantics | Test existing `/api/messages` (normal, validation, repeated submits/rate limit) and guest form feedback | Guest receives accurate "submitted for approval" confirmation; visibility only after approval; no rate-limit/RLS regression. |

**Release-wide checks (GB-02 through GB-04):**

- **Visual/responsive:** Compare at 375px, 430px, 768px, 1024px, 1440px+ (or equivalent actual widths); light and dark OS themes; long/short data; event-specific accent palette. Hero must read as intentional editorial hierarchy, card variants must be controlled, type/wrapping readable, no horizontal overflow, touch targets usable. Validate with actual screenshots, not just code review.
- **Content volumes:** Seed 0, 1, 5, 20, 21, 100, and 1,000+ approved messages **without production personal data**. Verify load-more, searching a message beyond first 20, sorting, count, grouping, long-entry expansion and last-page handling. Avoid unbounded data loading.
- **Moderation and concurrency:** Test two clients and admin; pending → approved, approved → rejected, delete, concurrent approvals and reload, active search, disconnected client/reconnect. Verify search respects moderation, count updates correctly and no cross-event mixing.
- **Accessibility:** Keyboard-only operation; focus visible; expand controls expose state; search results/loading announced; correct headings and time semantics; screen reader spot check; normal/reduced motion; contrast and zoom 200%/400%. No hover-only required actions.
- **Quality:** Run `npx tsc --noEmit`, supported ESLint command, `npm run build`, relevant test runner, browser smoke tests, and Lighthouse/mobile profiling when available. Set a *target* of strong Core Web Vitals and no perceptible long-task/jank with representative data, but do **not** invent a numeric score or claim 95+ without an actual run. Record instrumentation, environment, and any caveats.
- **Structural review:** No parallel old/new feed, duplicated business rules, orphan CSS or obsolete observer after replacement; clean component responsibilities and no secrets in the browser bundle. Regression smoke: event home, Message submit, Guestbook, Gallery, Admin moderation, canonical metadata, Navbar, PWA/offline returning route.
- **Migration verification:** If a new SQL migration is introduced, document applied environment and exact revision, least-privilege tests, existing-data invariants, backout/forward recovery, and production authorization. If no migration, record "Not applicable — no schema change".

**Reporting rule:** For each required check, report **Passed / Failed / Not run with reason**. Do not mark any iteration complete based only on a build or screenshot, and do not treat mocked/test schema results as proof of live production behavior.
